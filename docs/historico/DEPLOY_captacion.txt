QUÉ CAMBIA (resumen para vos)
────────────────────────────
Los registros que entran desde la web (alta autogestionada) ya NO se tratan
como "ventas". Ahora viven en un ciclo de CAPTACIÓN dentro de Leads:

        Nuevo (por verificar)  →  Verificado   /   Descartado

- En el detalle del Lead aparece el botón "Verificar ficha". Un solo clic:
    1) marca la empresa como VERIFICADA (ya no hace falta ir a "Empresas"),
    2) envía el correo de verificación al dueño (igual que antes),
    3) crea una OPORTUNIDAD de onboarding/bienvenida SIN asignar.
- Esa oportunidad cae arriba de todo en "Disparadores de venta" (Oportunidades),
  marcada "sin asignar" en rojo. Desde ahí la derivás manualmente al embajador
  con el selector que ya existía (POST /admin/signals/:id/assign).
- Los leads de VENTA reales (Destacado / Pro / promo boost / reclamos) mantienen
  intacto su pipeline comercial (Pendiente→Contactado→Negociando→Ganado/Perdido).

El discriminador de captación es el PLAN: la ficha gratis = plan 'basic' (o sin
plan) → captación. featured/premium/claim → venta. La marca notes.source=
'web_register' se respeta como señal extra. (Antes dependía sólo de source, pero
hay altas de ficha gratis que no la traen — p.ej. el caso "Showroom Syrocco".)
Front (isCaptacionLead en config.js) y backend (filtro ?origin) usan el mismo
predicado, así que KPIs y filtros siempre coinciden.

DEPLOY   (subís el .tar.gz a /home/hepta/claude/ · el proyecto vive en /opt/retopa/)
────────────────────────────
El tarball está rooteado en  opt/retopa/...  → se extrae directo con  -C /
y cada archivo cae exactamente en su lugar dentro de /opt/retopa/.

1) (Recomendado) Respaldo rápido de los archivos que se van a pisar:

      cd /opt/retopa && tar czf /home/hepta/claude/backup_pre_captacion_$(date +%F).tar.gz \
        backend/src/routes/admin.js frontend/admin/index.html \
        frontend/admin/js/config.js frontend/admin/js/leads.js frontend/admin/js/signals.js \
        frontend/embajador/js/opportunities.js

2) Extraer sobre la raíz (respeta la estructura /opt/retopa/...):

      tar xzf /home/hepta/claude/retopa_captacion_verify.tar.gz -C /

   Deja además las notas y los harnesses en  /opt/retopa/_deploy/
   (fuera del código; podés borrar esa carpeta cuando quieras).

3) Reconstruir y levantar:

      cd /opt/retopa && docker compose up -d --build

   No hay MIGRACIÓN de base de datos: el flujo reutiliza columnas existentes
   (service_leads.status como texto, sales_signals con product_target='onboarding').

3) (OPCIONAL) Personalizar la oportunidad de onboarding sin tocar código.
   Los valores por defecto ya funcionan (TTL 21 días + mensaje en voseo).
   Podés editarlos desde Admin → Disparadores de venta → Configuración, o por SQL:

      cd /opt/retopa && docker compose exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" <<'SQL'
      INSERT INTO site_config (key, value) VALUES
        ('signal_onboarding_ttl_days', '21'),
        ('signal_msg_onb_bienvenida',
         '¡{business} se sumó a RetoPA y ya está verificada! Contactá al dueño para darle la bienvenida, ayudarlo a completar su ficha y presentarle los planes.')
      ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;
      SQL

   {business} se reemplaza por el nombre comercial de la empresa.
